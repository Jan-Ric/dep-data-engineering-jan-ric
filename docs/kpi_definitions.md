# KPI Definitions

These metrics summarize modeled inverter-hour data and saved analysis tables. They support descriptive review, not diagnosis of real equipment faults.

| KPI | Definition and formula | Unit | Source | How to read it | Limitation |
| --- | --- | --- | --- | --- | --- |
| Performance Ratio (hourly, per inverter) | Mean valid hourly PR across inverter-hour rows; each row uses `PR = AC_POWER / (irradiance_kWh_m2 * installed_DC_kWp)`. The saved summary reports the pooled mean. | Unitless ratio | `output/tables/summary_statistics.csv`, processed metrics `PERFORMANCE_RATIO` row | Compare with 1.0 as a normalized reference; the pooled mean describes the modeled daytime fleet, not an individual inverter. | Only positive-irradiance rows have valid PR. The compact source is an aggregate, so this KPI does not provide the hourly series for each inverter. Weather, AC output, and fault windows are modeled or simulated. |
| PR gap | `1 - mean valid PR`, consistent with the project SQL definition of an absolute gap from 1.0. | Unitless ratio, often shown as percentage points | Derived from `output/tables/summary_statistics.csv` | Larger values indicate a greater distance below the reference PR of 1.0. | This is not a gap against a healthy-fleet baseline and does not establish a fault; baseline model PR can itself be below 1.0. |
| Flagged 3-hour block count | Sum of saved qualifying block counts across severity tiers. A block is a rolling set of three consecutive hourly records; each hour must have irradiance above 200 W/m² and non-null PR, and the 3-hour mean gap `1 - PR` must be at least 0.05. | Blocks | `output/tables/flagged_blocks_by_severity.csv`; rule in `sql/03_flagged_3h_blocks.sql` | Counts overlapping rolling windows, so one extended period can contribute more than one block. | Count is based on simulated data and a fixed rule. It is not a count of confirmed equipment failures. |
| Flagged inverter share | `inverters with at least one qualifying block / 830 inverters * 100`. | Percent of fleet | Fleet size from `README.md`; flagged-block aggregates in `output/tables/flagged_blocks_by_severity.csv` | Would show the portion of the fleet with one or more qualifying blocks. | Not available from the retained severity aggregate because it contains no inverter IDs. It is intentionally left unavailable rather than inferred from unrelated legacy rankings. |
| Severity distribution | For each tier, `tier block count / total flagged blocks * 100`; report Watch, Alert, and Critical counts and shares together. | Blocks and percent of flagged blocks | `output/tables/flagged_blocks_by_severity.csv` | Shows how saved flagged blocks are distributed by their 3-hour mean gap tier. | Overlapping blocks are counted separately. The SQL assigns exactly 0.20 to Alert and values above 0.20 to Critical; `docs/methodology.md` describes Critical as starting at 0.20, so that boundary should be reconciled before operational use. |
| Clipping hours share | `sample rows with AC_POWER >= 60 kW / sampled inverter-hour rows * 100`. | Percent of sampled inverter-hour rows | `output/tables/scatter_sample_100k.csv` | Estimates how often the modeled AC output reaches the 60 kW cap in this fixed-seed sample. | This is a sample estimate, not the exact fleet-wide share. The sample has no timestamp, so it cannot identify unique clock hours. Clipping is an expected model cap, not by itself a fault. |
| Fault detection rate | `injected fault windows detected by the fixed 3-hour rule / total injected fault windows * 100`. | Percent of injected windows | `output/tables/fault_detection_validation.csv` | Measures whether the fixed rule detected the known synthetic test windows. | There are only three configured synthetic windows; this is a rule check, not a real-world detection-performance estimate. |

## Thresholds

The saved three-hour query requires each of three consecutive hours to have irradiance above 200 W/m² and the three-hour mean PR gap to be at least 0.05. The query's severity bands are Watch for gaps from 0.05 up to but not including 0.10, Alert from 0.10 through 0.20, and Critical above 0.20. These are demonstration thresholds, not validated maintenance limits. The methodology document differs at exactly 0.20; the distinction is disclosed above rather than changing existing output values.

## Audience

The primary audience is an O&M engineer, who can use the metrics to prioritize records for review and verify the fixed detector against its test windows. A plant supervisor can use the fleet summaries to understand the scale and severity mix of modeled flags. Neither audience should treat a flag as a confirmed fault without real telemetry and investigation.
